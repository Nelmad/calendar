### QA-01 (P0): бесконечный цикл рендера при гидрации внутри Suspense

**Причина.** `useCalendarController` создавал `calendarModel(...)` заново на каждом рендере: validation, `validateRecords`,
сортировка и индекс по всем items, новый объект `model`. От него зависели commit-effect контроллера и главный effect
`MonthSurface`; `cell` и `recover` зависели от объекта `controller`, который тоже новый на каждом рендере. Поэтому эти
effects выполнялись после каждого рендера и вызывали `setAnchor(cell)`, `setNavigation(prev => same ? prev : next)` и
`setAgenda` с тем же значением. Обычно React отбрасывает такое обновление сразу (eager bailout). Внутри отдельно
гидрируемой Suspense-границы у fiber остаются pending lanes, bailout не срабатывает, и цепочка effect → setState →
render → новый model → effect не останавливается. То же следствие давало O(всех items) на каждый рендер: стрелка, клик,
любая перерисовка родителя.

**Исправление.**
- [`model.ts`](../../src/v02/calendar/model.ts): `createCalendarModel(services)` — memo на экземпляр. Каждая стадия
  мемоизирована по тем входам, которые читает: конфигурация — по поверхностному равенству props; locale — по
  `locale/firstDayOfWeek/hourCycle/dir`; сообщения — по locale, `timeZone`, `messagesLocale`, `messages`; records — по
  `items/sources/visibleSourceIds`; сортировка и проекция — по records, `timeZone`, `sortItems`; диапазон — по
  `anchorDate/timeZone/locale/firstDayOfWeek`; индекс — по сортировке и диапазону. Рендер с теми же входами возвращает
  тот же `model`. Новый callback или посторонний prop не пересчитывают records и индекс; навигация пересчитывает только
  индекс диапазона ([`layout.ts`](../../src/v02/core/layout.ts): `indexRange` над готовым `orderItems`).
- [`useCalendarController.ts`](../../src/v02/calendar/useCalendarController.ts): `snapshot` и `currentAgenda` зависят от
  значений, а равная реконсиляция повестки сохраняет прежний объект. `updateNavigation` не ставит в очередь равное
  состояние. `getDateCell` и `getFocusDate` стабильны (ref на зафиксированную roving-дату).
- [`CalendarMonth.tsx`](../../src/v02/calendar/CalendarMonth.tsx): `cell` и `recover` больше не зависят от объекта
  `controller`; `setAnchor` вызывается только при смене узла.
- `useToday`, `useRootName`, `useMonthMeasurements` и `useLayoutObserver` пишут state только при реальном изменении.
- Диагностика сообщений, раньше собиравшаяся заново на каждом рендере, стала очередью внутри memo; её выводят
  commit-effects (см. QA-23).
- [`examples/next`](../../examples/next/README.md): маршрут `/streaming` с `loading.tsx` и
  [`AutoSchedule`](../../examples/next/components/AutoSchedule.tsx) (`layout="auto"`, без `today`). Packed harness
  получил Suspense SSR-страницу для Vite ([`packed-probes/vite/src/suspense`](../../scripts/implementation/packed-probes/vite/src/suspense/Suspended.tsx))
  и проверку простоя.

### QA-04 (P1): `layout='auto'` переключается каждый кадр из-за полосы прокрутки

**Причина.** Каждая ширина из `ResizeObserver` сразу превращалась в layout по точной границе. Если полоса прокрутки
страницы (или предка с `overflow: auto`) есть только у более высокого desktop-месяца, desktop сужает корень ниже
границы, а mobile снова его расширяет: две ширины по разные стороны границы, по одной на layout, без устойчивого
состояния.

**Исправление.** [`useResponsiveLayout.ts`](../../src/v02/calendar/useResponsiveLayout.ts) и
[`switchFeedback`](../../src/v02/core/responsive.ts): каждое переключение, вызванное шириной, ещё раз синхронно
измеряется в layout effect своего же commit, до отрисовки и до любого действия пользователя. Если новый layout сам
вернул ширину через границу, это обратная связь: layout удерживается при этой ширине, пока ширина не изменится (уведомления
только о высоте ничего не решают; сравнение с допуском 0,5 px). Любое другое измерение по-прежнему решается точной
границей §7, в том числе 639/640 px и все реальные resize. Смена `mobileBreakpoint`, forced layout или контракт сбрасывают
удержание. Это закрывает петлю любой ширины полосы без временных окон и без гистерезиса на обычных resize. Правило
описано в [`api.md`](../api.md#prop-layout)/[`api.ru.md`](../api.ru.md#prop-layout) и в README.

**Tests.**

  сторон границы, нестандартного breakpoint и невалидных ширин.
- [`responsive.test.tsx`](../../src/v02/calendar/__tests__/responsive.test.tsx), «auto layout loop guard»: страница, где

**Остаточный риск.** В удержанном состоянии layout отличается от точной границы на ширину обратной связи (в примере
desktop при 630 px content box) — это сознательный выбор вместо мерцания, задокументирован. Обратная связь, которая
проявляется не в том же commit, а позже (например, асинхронная загрузка шрифта меняет высоту только одного layout),
ловится на следующем переключении. Удержание сбрасывается при любой смене ширины, поэтому шаговый resize окна внутри
полосы обратной связи даёт одно переключение на каждую установившуюся ширину, не петлю. Firefox/Safari не проверены.
*Позднее уточнение:* проверка QA-A показала, что именно это даёт чередование на каждом шаге перетаскивания через полосу
(QA-A-1-02), а удержание противоречит точной границе §7 без решения lead (QA-A-1-01); исправлено гистерезисом в
[раунде 1](#qa-a-fix-1).

### QA-13 (P2): недетерминированное восстановление focus в sheet при исчезновении item

**Причина.** Когда обновление данных удаляет сфокусированный item, Chrome при удалении узла синхронно шлёт `focusout`, и
`FocusScope` React Aria в sheet планирует перефокусировку первого control на следующий кадр. Восстановление §12.3 в
`CalendarMonth` выполнялось в passive effect. Обновление не из события пользователя выполняет passive effects отдельной
задачей, поэтому в медленной (development) сборке кадр почти всегда успевал раньше: focus оказывался на «Закрыть», и
passive effect уже не видел потерянного focus. Sheet оставался открытым. В production исход зависел от гонки.

**Исправление.** [`CalendarMonth.tsx`](../../src/v02/calendar/CalendarMonth.tsx): разбор потерянного owned focus вынесен
в `restoreOwned` и выполняется в layout effect того commit, который удалил узел, если presentation не менялась. Тот же
item/control в той же поверхности получает focus сразу; иначе overlay закрывается синхронным повторным рендером до
кадра (unmount `FocusScope` отменяет его кадр), а ячейка даты получает focus после снятия `inert`. Переходы между
presentations остаются passive: modal-эффекты новой поверхности должны предшествовать переносу focus (§11.3). Итог
одинаков в любой сборке: popover и sheet закрываются, focus — на ячейке даты, inline-повестка остаётся. В
[`api.md`](../api.md#prop-items)/[`api.ru.md`](../api.ru.md#prop-items) описаны это поведение и требование стабильных `id`
между загрузками.

  Ожидается закрытый sheet, focus на ячейке и ни одного `inert`. На прежнем коде все три падают.

раздел 7, п. 4) зафиксировано в api.md, но в спецификацию не вносилось.

### QA-23 (P3): диагностика для разработчиков

**Причины и исправления.**
- **Ложное `aria-labelledby` при размонтировании.** Callback `MutationObserver` в
  [`useRootName.ts`](../../src/v02/calendar/useRootName.ts) мог выполниться после удаления корня, но до cleanup effect
  (несрочное размонтирование, клиентская навигация Next в dev) и проверял уже отсоединённый корень. Теперь отсоединённый
  корень не проверяется; имя записывается только при изменении.
- **`messages` с функцией.** Диагностика `messages.<key>` для функции, вернувшей `''` или не строку, создавалась, но
  выводилась только commit-effect контроллера. Заголовок повестки рендерит только `MonthSurface`, без нового commit
  контроллера, поэтому предупреждение терялось. Теперь диагностика рендера копится один раз на ключ в memo модели, а
  выводят её commit-effects каждого компонента, который рендерит сообщения (`useMessageDiagnostics`).
- **Отсутствующий обязательный prop.** [`validation.ts`](../../src/v02/core/validation.ts): для отсутствующих `items`,
  `anchorDate`, `timeZone`, `onNavigate` — `Required; expected …` вместо причины разбора `undefined`. Невалидный
  `timeZone` по-прежнему называет accepted-set.
- **Пропсы 0.1.** [`surface.ts`](../../src/v02/surface.ts): «not available in 0.2.0-alpha.2» остаётся только для props,
  запланированных в следующих prerelease (`laterProps`; compile-time проверка, что `surfaceProps` и `laterProps` вместе
  совпадают с ключами §5.7). Любой другой prop, в том числе удалённый 0.1, сообщается как
  `not a 0.2 Calendar prop; 0.1 props were removed (docs/migration-0.1-to-0.2.md); ignored`. Список имён 0.1 в runtime
  не нужен (dist guard запрещает их в коде пакета).
- **`tokens.css`.** В [migration guide](../migration-0.1-to-0.2.md#removed-exports) уточнено: проверку типов не проходят
  именованные экспорты, а side-effect import `@nelmad/calendar/tokens.css` TypeScript не проверяет (без
  `noUncheckedSideEffectImports`), и он падает в бандлере или Node.

Диагностика описана в api.md (таблица Diagnostics, раздел Props not available), README и CHANGELOG.

### Раунд 1 исправлений QA-A (по проверке QA-A-1)

**QA-A-1-02 (P2): guard QA-04 чередовал layout на каждом шаге перетаскивания.** *Причина.* Удержание снималось при
любом изменении ширины на 0,5 px и больше. На каждом шаге resize через полосу обратной связи удержание снималось,
точная граница переключала layout, новый layout снова давал ширину по другую сторону границы, и удержание
восстанавливалось уже на другой стороне. Проверка показала 15 переключений на 15 px полосы прокрутки при шаге 1 px.
*Исправление.* [`responsive.ts`](../../src/v02/core/responsive.ts) (`withinFeedbackBand`) и
[`useResponsiveLayout.ts`](../../src/v02/calendar/useResponsiveLayout.ts) реализуют гистерезис. Переключение с обратной
связью запоминает полосу `band = |ширина после − ширина до|`, в примере это ширина полосы прокрутки. Пока ширина остаётся в
`[breakpoint − band, breakpoint + band)`, текущий layout сохраняется. В этой полосе либо показанный layout уже подходит
к точной границе, либо не подходит ни один. Вне полосы снова решает точная граница, и выбранный ею layout подходит и к
собственной ширине; полоса при этом забывается, и следующее пересечение измеряет свою обратную связь заново. Смена
breakpoint, forced layout и контракт сбрасывают полосу, как раньше сбрасывали удержание. Описание в
[`api.md`](../api.md#prop-layout)/[`api.ru.md`](../api.ru.md#prop-layout), README/README.ru и CHANGELOG исправлено: одно
переключение на пересечение полосы, в том числе при перетаскивании окна.
*Tests.* [`responsive.test.tsx`](../../src/v02/calendar/__tests__/responsive.test.tsx): новый test, шаги по 1 px через
полосу вниз, вверх и с разворотом внутри неё. Ожидается одно переключение на проход, а вне полосы на каждом шаге —
точная граница по собственной ширине layout. Прежний test «real resizes keep the exact boundary» переименован в
«widths outside the band follow the exact boundary», его последовательность и ожидания не менялись; test удержания
переименован («decides nothing inside its band»). [`core/__tests__/responsive.test.ts`](../../src/v02/core/__tests__/responsive.test.ts):
границы `withinFeedbackBand`. Chrome ([`responsive-probe.mjs`](../../scripts/implementation/responsive-probe.mjs), новый
сценарий «1 px resize steps» для Document/ShadowRoot): классические полосы прокрутки 15 px, окно 695 → 664 → 695 px и
разворот в середине полосы. Проходы выполняются дважды: с ожиданием 6 кадров на каждом шаге и с одним кадром на шаг
(ближе к непрерывному перетаскиванию). Вне полосы layout на каждом шаге проверяется по точной границе, на каждый проход
приходится ровно одно переключение, за 1 с покоя переключений нет.

нет устойчивого решения. Desktop измеряет ширину ниже границы, а mobile — не ниже: в примере desktop 625–639 px и mobile
640–654 px, в том числе mobile ровно при 640 px. Гистерезис не меняет этот факт, а только убирает мерцание. Любое

### Общее исправление: modal-эффекты пакета (T16-V3-01, основа для QA-03, QA-10, QA-20)

**Причина.** Sheet получал modal-эффекты из `useModalOverlay` React Aria: `ariaHideOutside` по умолчанию берёт корень
`document.body` глобального realm, `usePreventScroll` блокирует прокрутку глобального `document`, а `FocusScope contain`
возвращает focus из любого нового слоя. Для Calendar в документе iframe это скрывало родительскую страницу вместе с
iframe и открытым sheet и не трогало фон iframe. Для хоста это делало `inert` любой узел, добавленный позже, в том числе
диалог хоста из `onItemPress` (QA-10), и уводило из него focus.

**Исправление.** [`calendar/modality.ts`](../../src/v02/calendar/modality.ts) — собственные modal-эффекты пакета.
- Реестр на документ: все открытые modal-слои пакета в документе — один стек (agenda sheets, дочерние sheets, любые
  Calendar). Документ — `ownerDocument` портала sheet, никогда не глобальный `document`.
- Верхний слой делает `inert` (`aria-hidden` только там, где `inert` нет, например в jsdom) соседей на composed-пути от
  своего узла до `body` этого документа; путь проходит через ShadowRoot к его host. Узлы, уже скрытые хостом, не
  присваиваются и не открываются при закрытии. Не скрываются `script`/`style`, закрытые `<dialog>`, live announcer
  и top layer React Aria, а также non-modal overlays пакета, открытые после слоя (child menu).
- `MutationObserver` на документе и ShadowRoot пути пересчитывает фон при добавлении узлов и при изменении `open`,
  `aria-modal`, `role`, `hidden`.
- Блокировка прокрутки — `overflow: hidden` на `documentElement` этого документа, с компенсацией классической полосы
  прокрутки, как у React Aria. Снимается, когда закрывается последний слой документа. JavaScript не внедряет `<style>`
  (ветка iOS у `usePreventScroll` внедряла).
- Удержание focus: `focusin` вне слоя возвращает focus на последний control слоя. `Tab`/`Shift+Tab` в sheet идут по
  composed sequential order с переходом через края, без `preventScroll`, поэтому control прокручивается в видимую
  область. `Escape`, когда focus оказался вне поверхности (на `body`), закрывает верхний слой.
- Очистка при закрытии, unmount, смене presentation и container: каждый [`ModalSheet`](../../src/v02/primitives/ModalSheet.tsx)
  регистрирует слой в layout effect коммита монтирования (до начального focus и объявлений владельца) и снимает его в
  cleanup. Фон sheet закрывает его только нажатием на сам фон, без interact-outside React Aria.

**Tests.** [`hosts.test.tsx`](../../src/v02/calendar/__tests__/hosts.test.tsx): Calendar в документе iframe jsdom (другой
realm, `contentWindow !== window`). Фон iframe скрыт, его `documentElement` заблокирован, в родительском документе нет ни
одного скрытого узла и блокировки, Tab остаётся в sheet, `Escape` чистит всё. Ещё: `Escape` при focus на `body`
закрывает sheet и возвращает focus на ячейку; нажатие внутри sheet не закрывает его, нажатие на фон — закрывает.
Chrome, overlay probe (`evidence/qa-fixes-2026-10-09/QA-B/overlay/browser.json`), два новых сценария «T16-V3-01
cross-realm iframe»: модуль работает в верхнем окне и рендерит Calendar в документ iframe того же origin; sheet и sheet +
modal child. Проверяется: фон iframe `inert` (не только `aria-hidden`), прокрутка iframe заблокирована, родительский
документ без `inert`/`aria-hidden` и блокировки. По дереву accessibility Chrome (CDP `Accessibility.getFullAXTree`) sheet
остаётся в дереве iframe, фон iframe — нет, кнопки страницы и сам iframe — да. Tab остаётся в sheet iframe, после
`Escape` всё снято и focus на ячейке. Все прежние same-realm сценарии зелёные: overlay **48/48** (46 + 2),
регрессии ниже.

**Остаточный риск.** Popover в документе iframe позиционирует React Aria. Его `calculatePosition` читает глобальные
`window`/`document`; разовая проверка (popover у ячейки в iframe со смещением) положение не исказила, но в probe это не
закреплено. Хост-слой распознаётся по разметке (`<dialog>` modal, `aria-modal`, `role=dialog/alertdialog`); модалка без
этой разметки останется фоном. Firefox/Safari и iOS не проверялись; для iOS прежний обход React Aria (touch-handling,
`overscroll-behavior` через `<style>`) заменён на `overscroll-behavior: contain` в `styles.css`.

### QA-02 (P1): desktop popover agenda нельзя прокрутить

**Причина.** [`NonModalPopover`](../../src/v02/primitives/NonModalPopover.tsx) слушал `scroll` в capture на документе и
вызывал `updatePosition()` на любой scroll, в том числе на прокрутку самого popover. `updatePosition` временно сбрасывает
`max-height` позиционера до высоты viewport. Внутренний скроллер (`max-block-size: inherit`) при этом растёт, и
`scrollTop` зажимается, а якорь прокрутки React Aria смотрел на позиционер (`scrollRef` по умолчанию), а не на скроллер.

настоящий скроллер `.nc-popover`, поэтому пересчёт от прокрутки страницы сохраняет положение сфокусированного control.
`overscroll-behavior: contain`: конец длинного списка не прокручивает страницу под popover.

### QA-03 (P1): agenda внутри модальных диалогов хоста

**Причина.** Портал по умолчанию — `body`. Модальный хост делает `inert` всё вне себя (нативный `showModal()`, top
layer), держит focus (focus-trap) или выключает события указателя на `body` (Radix/shadcn), поэтому agenda в `body` была
недостижима. С `portalContainer` = диалог popover считал viewport границей и обрезался боксом диалога.

**Исправление.** *Решение lead:* цель по умолчанию остаётся внутри ближайшего открытого модального контейнера корня.
[`portal.ts`](../../src/v02/calendar/portal.ts) `dialogContainer` — ближайший composed-предок корня: `<dialog>` в
состоянии `:modal`, элемент с `aria-modal="true"` или `role="dialog"`/`"alertdialog"`, иначе `ownerDocument.body`. Цель
вычисляется при монтировании и заново при каждой activation даты (`refresh`; диалог мог открыться вокруг уже
смонтированного Calendar). Смена цели по умолчанию при открытом overlay закрывает стек так же, как смена identity
(R53). Явный `portalContainer` по-прежнему главнее.
- Popover получает `boundaryElement` = этот диалог. React Aria смешивает координаты контейнера и viewport, когда граница
  сама является containing block, поэтому каждое размещение дополнительно вписывается в видимую часть границы по
  направлению роста.
- Overlays пакета принимают события указателя при `body { pointer-events: none }`.
- `Escape` в повестке и раньше вызывал `preventDefault`; теперь событие возникает внутри диалога, и `cancel` нативного
  `<dialog>` не наступает.

Это отступление от буквы §10.3.4 («default — `Calendar` root `ownerDocument.body`») для Calendar внутри модального хоста;
вне хоста поведение прежнее. *Позднее уточнение:* по [решению 2](decisions-2026-10-09.md#decision-2) (spec draft v7) цель по
умолчанию — только открытый modal container (`<dialog>` в `:modal` или `aria-modal="true"`). Распознавание `role="dialog"`/
`"alertdialog"` без `aria-modal` убрано, вместе с этим исправлены QA-B-1-03 и QA-B-1-05. Записано в api.md/api.ru.md (`portalContainer`), README/README.ru, CHANGELOG и story
`Portals`; в спецификацию не вносилось.

**Tests.** `hosts.test.tsx`: popover и sheet по умолчанию внутри `role=dialog aria-modal` хоста; для sheet `inert` —
содержимое хоста позади и страница, но не сам хост; диалог, открытый вокруг смонтированного Calendar, используется со

- Нативный `<dialog>` desktop: popover в диалоге, hit-test внутри, Tab, первый `Escape` закрывает повестку, второй —

- Pointer-events хост (`role=dialog` без `aria-modal`) и он же с явным `portalContainer={document.body}`: нажатие item
  доходит.

**Evidence** (QA-03 (`evidence/qa-fixes-2026-10-09/QA-03/manifest.json`)): `f0-modal-hosts.mjs` и `f3-dialog-portal-clip.mjs`

### QA-10 (P2): модалка деталей из `onItemPress` внутри modal sheet

**Причина.** См. общее исправление: новый узел хоста становился `inert`, `FocusScope contain` забирал focus, нажатие по
модалке хоста закрывало sheet как outside press.

**Исправление.** По §12.2 sheet закрывают только `Escape`, close, нажатие на фон и handoff §5.3, поэтому sheet не
закрывается, а *уступает*. Слой хоста, появившийся поверх стека (`<dialog>` modal, `aria-modal`,
`role=dialog/alertdialog` вне UI пакета, которого не было при открытии), никогда не становится `inert`. Пока он открыт,
стек не удерживает focus, не обрабатывает `Escape` и опускается под него: `data-yielded` на фоне → `z-index: auto`. Нажатие
внутри слоя хоста не закрывает sheet: фон закрывает только нажатие на него самого. Если нативный `<dialog>` хоста
показан, когда его предок ещё был фоном, и focus остался на `body`, focus переносится в первый control диалога. Когда слой
закрывается, sheet снова модален, и если хост не вернул focus, sheet фокусирует нажатый control. Описано в
api.md/api.ru.md (`onItemPress`, sheet), README, CHANGELOG.

**Tests.** `hosts.test.tsx`: портальная модалка хоста из `onItemPress` видна, не скрыта, ввод `hello`, Tab по ней,
`data-yielded`. После закрытия sheet открыт, `data-yielded` снят, focus на нажатом item, Tab снова внутри sheet, `Escape`
всё чистит. Chrome, host probe: портальная `aria-modal`-модалка и нативный `<dialog>`. Модалка не скрыта и находится
сверху по hit-test (обе стороны не `inert`). Ввод, Tab, закрытие с клавиатуры, возврат focus на `task-1`, удержание focus
снова работает, фон снова `inert`.

До: sheet/portal и sheet/native — `hostInert: true`, ввод теряется, нажатие «Close» перехватывается

заставит стек уступить; focus при этом не переносится, если он был в sheet.

### QA-20 (P3): Escape сразу после activation

**Причина.** Effect, принявший intent, вызывал `setMounted(rule.open)`. Если `Escape` (или любая клавиша, pointer, уход
focus) отменял intent до коммита монтирования, overlay всё равно монтировался, а следующий проход effect выходил на
`if (!request) return` без начального focus: sheet открыт, focus на `body`, фон `inert`.

**Исправление.** [`CalendarMonth`](../../src/v02/calendar/CalendarMonth.tsx): ref `opening` запоминает overlay, который
запросил intent. Если к коммиту монтирования intent отменён, а смонтирован именно этот overlay, он сразу закрывается
обычным `close()`: modal-эффекты снимаются, focus возвращается на ячейку даты (§5.2.1/§8 — отмена intent не открывает
overlay). Независимо от этого `Escape` при focus вне поверхности закрывает верхний modal-слой (общее исправление).

**Tests.** [`opening.test.tsx`](../../src/v02/calendar/__tests__/opening.test.tsx): обёртки `ModalSheet`/`NonModalPopover`
нажимают клавишу в коммите монтирования, до passive effect владельца, — детерминированная форма гонки. Для sheet и
popover проверяются `Escape` и `Shift` (`Shift` проверяет именно путь effect, без обработчика `Escape` слоя). Ожидается:
диалога нет, focus на ячейке, нет `inert`, фона и блокировки; следующая activation открывается с focus внутри. Chrome,
host probe: popover, sheet, controlled sheet × 5 дат × keyboard/pointer с `Escape` сразу следом — 0 открытых из 10.

**Evidence** (QA-20 (`evidence/qa-fixes-2026-10-09/QA-20/manifest.json`)): `f1-escape-race.mjs` и `f1-gap.mjs` судьи на
production-фикстуре. До: 5–10 из 10 overlays остаются открытыми, в детерминированном проходе sheet открыт с focus на `body`,

### QA-14 (P2): внедрение CSS через значение токена в SSR

**Причина.** `themeStyle` передавал строку токена в `style` корня как есть. React SSR пишет её в атрибут без экранирования
`;`, поэтому значение `white;position:fixed;…` становилось несколькими декларациями, а клиентский рендер (CSSOM
`setProperty`) отвергал его целиком: сервер и клиент расходились, гидрация сохраняла внедрённые декларации.

**Исправление.** [`themes/classic.ts`](../../src/v02/themes/classic.ts) `isDeclarationValue`: строка должна быть одним
CSS `<declaration-value>`. Без разбора CSS и без `CSS.supports` отвергаются только структурные нарушения: `;` или `!` на
верхнем уровне (в том числе `!important`), незакрытые строка, комментарий, скобка или `url(`, лишняя или чужая
закрывающая скобка, кавычка или `(` внутри `url(` без кавычек, `\` в конце. Такое значение трактуется как отсутствующее
поле с предупреждением `tokens.<group>.<token>: Expected a single CSS declaration value`, на сервере и на клиенте одинаково.
Строки внутри кавычек, скобок и `url(…)` с `;` допустимы. Дополнительно цвета токенов в `styles.css` пишутся в
`background-color`, а не в shorthand `background`: значение `url(…)` в цветовом токене больше не загружает изображение.

*Трактовка.* §10.3.2 говорит, что непустые строки передаются «как CSS component values без нормализации», и требует
одинаковых inline-деклараций на сервере и клиенте. Строку, которая не является одним значением декларации, React не может
передать одинаково, поэтому она приравнена к пустой. Это расширение списка «отсутствующих» значений; R63 и
`S10.3.2-2c15227a264d` получили partial evidence с этой оговоркой, подтверждение lead нужно до `pass`. *Позднее уточнение:*
трактовка одобрена как правило безопасности §10.3.2 spec draft v7 ([решение 3](decisions-2026-10-09.md#decision-3)).

### Раунд 1 исправлений QA-C (по проверке QA-C-1)

Evidence раунда — QA-C-fix-1 (`evidence/qa-fixes-2026-10-09/QA-C-fix-1/`). Прежние каталоги QA-C, QA-14 и QA-16 не

`sha512-7D0GQj0mhE5Xb6GwROPo+7f6cPrY4MyTcu9qTT3w0kQOt81osB0cab4NkEaNqiO0R2lUAZqRAXv5Hp+jUogVXQ==`; тот же архив дал
packed-прогон (`evidence/qa-fixes-2026-10-09/QA-C-fix-1/packed/manifest.json`) и воспроизведение CSP.

**QA-C-1-01 (P1): обход проверки QA-14 через экранированный `url(`.** *Причина.* `isDeclarationValue` узнавала `url(` без
кавычек только по четырём исходным символам перед `(`. CSS декодирует экранирование в идентификаторе, поэтому `u\72l(`,
`\75 rl(`, `U\52L(` и `ur\l(` — тоже `url(`. Кавычка внутри делает из него bad url, который кончается на первой `)`, а
проверка читала ту же кавычку как начало закрытой строки: на сервере `;` после `)` начинал новые декларации, клиентский
`setProperty` значение отвергал. Сравнение с разбором Chrome нашло ещё два пути той же природы. После `url(` проверка
пропускала пробелы JavaScript (`\s`, в том числе U+00A0), а CSS пропускает только свои: `url(U+00A0"a);position:fixed;…`
проходил. React пишет в атрибут `trim()` значения, поэтому `\` перед завершающей табуляцией становился экранированием в
конце и поглощал следующую декларацию.
*Исправление.* [`classic.ts`](../../src/v02/themes/classic.ts): проверка следует токенизатору CSS Syntax §4.3 во всём, что
определяет конец декларации: комментарии, строки и bad string, экранирование, идентификаторы с декодированием (`url`
сравнивается без учёта регистра ASCII уже после декодирования), числа и размерности (`1url(` — не `url(`), hash и
at-keyword (`#url(`, `@url(`), CDO, url token и bad url (кавычка, `(`, пробел внутри, управляющий символ). Проверяется
значение после `trim()`, а `trim()` обязан совпадать с обрезкой пробелов CSS; иначе (U+00A0, U+FEFF по краям) значение

**QA-C-2-01 (P1): восстановление при строгом CSP применяло заблокированные декларации.** *Причина.* `restoreServerStyle`
раунда 1 копировал весь текст серверного атрибута `style` в `element.style.cssText`. В атрибуте корня есть и root `style`
потребителя, который не проверяется. React пишет значение с `;` верхнего уровня в серверный HTML текстом, и `cssText`
после гидрации читал его как дополнительные декларации (`position: fixed`, `z-index`, `outline`). CSP заблокировал их, а
клиентский рендер их не пишет: React применяет `style` по одному свойству (`setProperty` для custom properties,
присваивание для остальных), и такое значение отвергается целиком. Восстановление обходило CSP для того же класса
инъекций, который QA-14 закрыл для `tokens`. Утверждения раунда 1 «итог совпадает с клиентским рендером» (отчёт), «the
same declarations through CSSOM» (README) и «the same declarations apply» / «as a client render does» (ledger) были
неверны.
*Исправление.* [`serverStyle.ts`](../../src/v02/primitives/serverStyle.ts): `restoreServerStyle(element, style)` больше не
читает текст атрибута. Атрибут служит только признаком серверного элемента: если он есть, а блок деклараций пуст,
записывается объект `style` того рендера, который закоммитила гидрация, по одному свойству, тем же путём, что
`setValueForStyle` react-dom на клиенте. Custom property — `setProperty` (React 18 обрезает значение, React 19 нет).
Число без единицы получает `px`, кроме свойств из таблицы unitless react-dom, выбранной по `version` из `react`: в React 19
есть `scale` и фиксированный список префиксов, React 18 выводит префиксы для каждого свойства. `float` пишется как
`cssFloat`, а пустое значение, `null` и boolean — как пустая строка. Поэтому декларацию, которую отверг бы клиентский рендер,
отвергает и восстановление. Hook `useServerStyle(ref, style)` запоминает объект первого рендера. Корень
([`ThemeRoot.tsx`](../../src/v02/primitives/ThemeRoot.tsx)) передаёт `themeStyle(tokens, style).style`, сетка
([`MonthView.tsx`](../../src/v02/calendar/MonthView.tsx)) — свой объект `--nc-week-count`/`--nc-minimum-row`; вызов
сетки перенесён после вычисления этого объекта (измерение строк — пассивный effect, порядок с ним не меняется).
Документация: README/README.ru «Content Security Policy» (стили пишутся заново по одному свойству, как при клиентском
рендере, а не текстом атрибута; отвергнутое клиентом остаётся отвергнутым), CHANGELOG (Fixed, та же оговорка), [api.md](../api.md#prop-style)/[api.ru.md](../api.ru.md#prop-style)
`style`: значения не проверяются, React пишет их в серверный HTML текстом, и значение с `;` становится там
дополнительными декларациями. Значения из настроек пользователя или арендатора нужно передавать через `tokens`.

### QA-06 (P2): ячейка с `:focus-visible` перекрывала свои chips и bars

**Причина.** `.nc-day:focus-visible { z-index: 1 }` поднимал сфокусированную ячейку над слоем сегментов той же недели
(`.nc-month-segments` без z-index). Попадание в chip находило gridcell: клик открывал повестку вместо `onItemPress`.

**Исправление** ([`styles.css`](../../src/v02/styles.css)). Ячейка больше не получает z-index. Кольцо фокуса рисует
`::after` ячейки (та же геометрия: 2 px, отступ 1 px внутрь) с `z-index: 2` и `pointer-events: none`: оно над items, а
нажатие проходит к item. Корень календаря и grid получили `isolation: isolate`, так что внутренние уровни (кольцо,
баннер статуса, sticky-строка) не соперничают со слоями хоста.

**Tests.** [`classic.test.tsx`](../../src/v02/themes/__tests__/classic.test.tsx): у правил ячейки нет z-index, кольцо —
`::after` с `pointer-events: none`, корень изолирован. Month probe (Chrome): клавиатурный фокус на дате, `elementFromPoint`
в центре chip — chip, клики по chip и по bar той же даты дают `onItemPress` (`design`/`bar`, дата 2026-03-04), повестка не
открывается; computed `::after` — `2px`, `z-index: 2`.

**Evidence** (QA-06 (`evidence/qa-fixes-2026-10-09/QA-06/manifest.json`)). До: в Vite-примере клик по «10:00 Планёрка»

**Остаточный риск.** Кольцо может частично закрывать края items в своей ячейке (по 2 px); Firefox/Safari не проверялись.

### QA-07 (P2): статус refresh/error сдвигал сетку, блокирующие состояния схлопывали высоту

**Причина.** Регион статуса стоял в потоке перед `.nc-calendar-view`: каждая загрузка вставляла его и сдвигала сетку
на ~88 px (ошибка с Retry — больше), а в `loading/initial` и `error/initial` вид удалялся целиком, и корень сжимался до
высоты текста статуса.

**Исправление** ([`CalendarShell.tsx`](../../src/v02/calendar/CalendarShell.tsx), `styles.css`).
- Неблокирующие статусы (`loading/refresh`, `error/refresh`) — регион нулевой высоты в том же месте DOM (перед видом,
  порядок Tab и чтения прежний) с баннером `.nc-calendar-status-banner`, который `position: absolute` перекрывает строку
  дней недели по центру. Сетка, открытый popover и начатое нажатие не двигаются. Баннер прогресса не перехватывает
  нажатия; кнопка Retry в баннере компактная (24 px, минимум §12.5), чтобы баннер помещался в строку дней недели.
- Блокирующий статус получает `data-weeks` (4/5/6) и `flex-basis` = недели × `dayMinHeight` + строка дней недели (в
  mobile — недели × 52 px + inline-повестка): высота календаря почти не меняется (628 → 632 px в Vite-примере). Через
  `flex-basis`, а не `min-height`, поэтому definite высота корня по-прежнему ограничивает его.
- Регион загрузки и progressbar названы видимым текстом через `aria-labelledby` (раньше то же имя трижды:
  `aria-label` региона, текст, `aria-label` progressbar). Регион ошибки сохраняет своё имя (`aria-label`).
- Проверка alpha-acceptance `refresh-status-spacing` переписана под новое расположение: для refresh-состояний сетка
  стоит там же, где в `ready`, баннер лежит в строке дней недели и не закрывает ни одной ячейки; для empty — прежний

**Tests.** [`controller.test.tsx`](../../src/v02/calendar/__tests__/controller.test.tsx): refresh-статус — `overlay`, перед

### QA-08 (P2): объявление месяца перезаписывалось статусом refresh; live regions внутри `aria-busy`

### QA-12 (P2): клик по частично скрытой ячейке терялся

### QA-18 (P3): lanes, `+N` и измерения сетки

**Причина.**
- `fitWeekLanes` резервировал строку `+N` для всей недели, если переполнялась хотя бы одна дата.
- Метрики строк ключевались по дате начала недели и записывались из `requestAnimationFrame` после ResizeObserver: новый
  месяц один кадр рисовался без lanes, уменьшение высоты — один–два кадра с items поверх строк.
- Размеры брались из `getBoundingClientRect` (визуальные px) и записывались как CSS px: `zoom`/`transform` у хоста
  искажали lanes.
- Comfortable: строка 120 px с границей 1 px вмещала на 1 px меньше двух lanes.
- Продолжения timed bar повторяли время начала; части по обе стороны пропущенной даты (Apia) не были продолжениями.

**Исправление.**
- [`layout.ts`](../../src/v02/core/layout.ts): лимит lanes считается по дате — дата, где все её items помещаются, сохраняет
  все lanes; строку `+N` получает только дата, которая иначе скрыла бы items (§6.3: N — по дате). Полоса, пересекающая оба
  вида дат, рисуется частями, у обрезанных сторон `continuesBefore/After`. Флаги продолжения считаются от всего членства
  item, поэтому части у пропущенной даты тоже продолжения.
- [`useMonthMeasurements.ts`](../../src/v02/calendar/useMonthMeasurements.ts): метрики по индексу строки; computed sizes
  (CSS px, округление до 1/64 px — единицы layout), так что zoom и transform хоста не влияют; новая ревизия (месяц, density,
  layout, язык) измеряется в layout effect до отрисовки; ResizeObserver применяет измерение через `flushSync` внутри своего
  callback — до отрисовки кадра с новым размером.
- `MonthView.tsx`: у сегмента с `continuesBefore` время не выводится.
- `styles.css`: comfortable `dayMinHeight` — 128px (было 120px): две lanes, как в compact. README, api.md (оба языка) и
  CHANGELOG обновлены.

**Tests.** [`layout.test.ts`](../../src/v02/core/__tests__/layout.test.ts): резерв по дате и разрезанная полоса; флаги Apia.
Month probe, отдельные сценарии: резерв по дате и продолжение без времени; каждый отрисованный кадр resize 1100 → 700 → 1000
и навигации туда-обратно без item поверх строк и без пустых строк (замер в ResizeObserver, созданном в rAF кадра, — после
observer календаря); lanes одинаковы без трансформаций и при `zoom: 1.5`, `scale(0.5)`, `scale(0.8)`; compact и comfortable
показывают по два item без `+N`.

**Evidence** (QA-18 (`evidence/qa-fixes-2026-10-09/QA-18/manifest.json`)). До: среда с двумя помещающимися items — один и
«+1»; после 1100 → 600 два отрисованных кадра с 70 items поверх строк; навигация рисует кадр с 4–5 пустыми строками; при

**Остаточный риск.** Решение «резерв по дате» выбрано по §6.3 («N — число items этой даты … в ячейке»); если lead
трактует строку о резерве как недельную, это изменение нужно откатить (открытый вопрос). Части полосы при смешанных датах
— новая визуальная форма. `flushSync` в callback ResizeObserver синхронно рендерит календарь при каждом изменении размера
строк.

**QA-D-3-03 (P2): объявление месяца заменялось «Обновление календаря» (решение lead 5).** *Исправление.*

urgent при ошибках, перенос focus на блокирующий регион подавляет объявление, `refreshCompletedAnnouncement` ровно один раз на
